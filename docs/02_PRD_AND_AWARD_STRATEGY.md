# 02 · 产品需求与获奖策略

> 状态：开发规格，尚未实现或完成验收。规则事实核查见 `01_AUDIT_AND_RULES.md`；本章产品取舍是设计判断，不是评委意见或获奖概率预测。

## 1. 唯一产品方向

**RecallLedger — the wallet assistant that remembers what your transfers mean.**

中文定位：**会记住用户纠正的链上支出助手**。服务于使用 Sui 接收报酬、支付工具费用或与合作方转账的独立开发者、自由职业者。这个目标用户与痛点目前是待试用验证的假设，不包装成已验证市场需求。

用户的核心问题是：“同一地址的转账可能是工具费、内部划转或报销，我不想每次都重新解释；助手也不能因为我解释过一次，就把以后所有转账都算成消费。”

完整用户闭环：

1. 输入一个支持的 Sui 主网交易摘要，Tatum 提供交易事实。
2. 未标注用途的转账显示 `needs_context`，不计入消费预算。
3. 用户补充业务用途，助手提出范围明确的可复用规则。
4. 用户确认规则后，持久化到 Walrus Memory。
5. 下一会话遇到范围内的新交易，直接引用规则归类，减少重复追问。
6. 用户指出反例后，系统更正这一笔，并提出收窄后的规则；仍需确认。
7. 新进程或 CLI 从 Walrus 恢复同一规则，产生相同结果；每个判断都可回放。

**唯一主赛道：Smart Agents for Real Life。专项优先级：Best Walrus Memory。** 主线不实现自动支付，不为了 AI Builder 奖改变 dot 开发方式。AI Builder 专项只在真实符合主办方 `built primarily with ai.tatum.io` 条件并能如实披露时申报。[官方规则](https://thewalrussessions.wal.app/tatum-total-recall/)

## 2. 为什么不继续原来的“大满贯”架构

| 原方案部分 | 处理 | 原因 |
|---|---|---|
| 市场/体育预测和信源信誉分 | 删除 | 与钱包支出闭环无关；需要另一套结果数据与统计评价 |
| 泛用研究代理 | 暂缓 | 用户价值需要另行验证，Tatum 容易成为装饰 |
| 自动放宽支付限额 | 删除 | 用户纠正用途不能构成增加资金权限的依据 |
| 自定义 x402-sui-direct 网关 | 删除 | 自定义 HTTP 402 不证明符合 x402/MPP；无助于本产品核心闭环 |
| 一次 Tatum AI Builder 脚手架作为获奖保证 | 删除 | 初始生成不能自行证明产品主要由该工具构建 |
| 12 条状态与时间轴 | 保留并重做 | 每条必须有实际因果作用，区分合成输入、真实持久化和已观察主网事实 |
| 可验证证据与跨会话恢复 | 强化 | 直接证明赞助方集成改变了产品能力 |

方案的竞争力来自一个能独立检验的闭环。增加赛道数量并不等于提高获奖机会；本次没有足够依据计算奖金期望值或给出获奖百分比。

## 3. 价值边界和证据分层

| 层级 | 能证明什么 | 不能证明什么 | UI 标签 |
|---|---|---|---|
| Tatum 交易事实 | 已核验网络、交易状态、完整资产类型、地址与金额等 | 商家身份、购买目的、税务性质、是否骗局 | `Onchain facts verified` |
| 用户说明 | 用户给过某个分类/关联/范围确认 | 该说法在现实世界必然正确 | `Context confirmed by you` |
| 规则引擎 | 当前输入符合哪条明确规则、计算如何得出 | 规则对所有未来情况都正确 | `Applied rule v2` |
| LLM 提议 | 在给定证据上提出 schema 可验证的候选规则或解释 | 自主确认规则、扩大权限、修改金额 | `Suggested — review required` |
| Walrus 回执 | 指定内容被提交并能按验证流程恢复 | 内容本身是真实世界事实或永久保存 | `Memory persisted` |

数据库可以完成分类，Walrus 的产品价值是用户可恢复、跨工具携带、带证据的记忆。必须用无应用缓存的恢复演示证明这件事，不能声称普通数据库无法存储记忆。

## 4. 范围和默认技术路线

采用单 owner 产品：React/Vite + TypeScript 前端、Fastify 后端、Postgres 本地状态和 outbox、Tatum 只读 provider、Walrus Memory 适配器。服务端持有 API 凭据；公开演示仅能读和回放。架构、数据契约以对应工程文档为准。

MVP 先支持一种明确资产及简单转账形态。演示 fixture 用 `TEST_USDC`，它不是主网 coin type。真实资产必须通过官方资料和当前 provider 返回的完整 coin type 核查，不能按 symbol 自动认作 USDC。金额以最小单位整数 string 存储与传输、用 BigInt 计算。若加入 SUI，gas 与 principal 必须分开，无法可靠拆分的交易转入 `unsupported`。

主线不做：银行/邮箱 OAuth、家庭多成员账本、全链扫描、法币换汇、投资/税务结论、真实钱包托管、自动支付、后台爬虫、自研智能合约、多模型投票、模型训练。项目上限由验收闭环决定，不按功能数量决定。

## 5. 功能要求

| ID | 功能 | 验收条件 |
|---|---|---|
| FR-01 | 输入并核验交易 | 支持形态得到可信 facts；错误网络、失败交易、无关 owner、复杂 PTB、provider 故障有明确状态 |
| FR-02 | 保留未知用途 | 默认 `needs_context`；未知金额单列，不算消费也不算收入 |
| FR-03 | 单笔标签与更正 | 只有 operator session 可写；用户标签与链事实分开；更正不改写原证据 |
| FR-04 | 提议可复用规则 | network、完整 asset、方向、counterparty、整数金额范围、有效期明确；LLM 不能省略硬条件 |
| FR-05 | 用户确认与持久化 | 规则只有用户确认且持久化完成后才影响新判定；pending/failure 不伪装 active |
| FR-06 | 确定性归类 | 同 facts、同策略快照必得同结果；显示 reason codes 和使用的规则版本 |
| FR-07 | 反例与范围收窄 | 先只更正明确目标交易；新范围需要重新确认；不能扩大其他谓词 |
| FR-08 | 撤销和到期 | 停止未来使用；旧 `as-of` 决策仍可重放；不声称物理删除远端 blob |
| FR-09 | 退款关联 | 只能冲回明确关联的原条目；核查方向、资产、owner、金额及累计退款上限；不能把所有入账当退款 |
| FR-10 | 预算汇总 | 仅 `expense` 且 category=`tools` 计入 Tools；明确关联退款冲回；其他类别/未知单列 |
| FR-11 | 跨表面恢复 | 空状态独立 Node 进程/CLI 从精确 manifest 恢复；与 Web 投影 hash、结果一致 |
| FR-12 | 固定输入对照 | memory off/on 使用同一输入 hash、域引擎和其他设置，仅改变历史记忆 |
| FR-13 | 公开只读评审 | 无需评委提供私钥即可看解释/脱敏证据；公开界面不能触发主网写入 |
| FR-14 | 提交材料 | 真实完成的10+主网 memory、公开 repo、可访问 demo、已发表博客、2–3分钟视频及实际表单字段逐项可核验 |

FR-14 的外部要求来源：[官方规则](https://thewalrussessions.wal.app/tatum-total-recall/)及[官方活动入口](https://tatum.io/hackathon/total-recall)。发布/提交是否获授权由执行会话上下文判断，准备材料与核验可自主完成。

## 6. 统一领域语义

分类枚举：`needs_context | expense | internal_transfer | reimbursement | refund | income`。

规则状态：`proposed | active | superseded | revoked`。到期是有效性谓词，不需要新增 `expired` 持久化状态；UI 可以显示 `Expired`。

优先级：有效的单笔用户标签/更正 → 满足全部谓词的唯一有效规则 → `needs_context`。多个有效规则冲突时请求澄清，不按语义检索排序或时间戳碰巧选一条。

`reimbursement` 在本 MVP 的 Tools 预算中默认不计入。它不代表普遍会计政策，只是该用户明确的预算口径。退款必须关联到之前已计入 Tools 的具体条目，不能由“同地址入账”自动推断。

规则收窄、撤销影响未来的自动判定。已经记录的旧决策保留其历史上下文；只有明确针对交易的 correction 才修改该交易当前有效分类。所有更改能查看前后差异。

## 7. 12 事件演示的唯一叙事

`fixtures/demo-sequence.json` 是场景计划，不是主网证据，也不是最终事件 schema。应用事件 schema 由数据契约文档定义。场景记录在同一专用 demo account/namespace；不能使用 namespace 作为隐私边界。

序列为：预算口径 → A未知 → A标工具费 → v1确认 → B复用 → C误归类 → C纠正为报销 → v2收窄 → D入账未知 → D关联为B退款 → E再次25时请求说明 → 撤销规则。

其中金额均为合成输入：A/B 为12 USDC，C/E为25，D为12入账；v1为5–30，v2为5–20；这两个范围由用户明确提供/确认，不得由单个12的样本推断。Tools 金额随序列为12→24→49→24→12；未标注E单列25。撤销不会偷偷抹去历史已记录的B分类。冷恢复、CLI、memory off/on 不应创建第13条主网记忆。

若实际使用合成输入保存到主网，UI/博客/视频须同时说明：**情景输入是合成的，存储/恢复调用是真的。** 主线还必须有至少一条真实Tatum主网读取。真实交易→用途标签→记忆→恢复的完整案例为P1加分实验，使用另一个显式scope/namespace并计入同owner总量；缺少真实用途时不阻断P0，也不拿fixture冒充它。参见08。

## 8. 产品成效与验收

主指标：范围内重复确认次数、范围外错误自动归类次数、冷恢复一致率、Web/CLI一致率、每个结果的证据可追溯性、耗时与外部调用费用。以上均是待测量指标。

安全的无记忆基线选择追问是正确行为。记忆的收益应是减少范围内重复追问，并保持范围外未知，不要求无记忆系统犯错来衬托提升。

测试集和门槛见 `08_EVALUATION_AND_ACCEPTANCE.md` 与 `fixtures/eval-cases.json`。作者先亲自试用；如有条件再找1–2名潜在用户试做“纠正→新会话→反例→恢复”，保存真实观察；人数少只做方向性证据。未做访谈不得写“用户喜欢”“节省X%时间”。

## 9. 如何对应评审

| 评审项 | 本项目应展示的证据 |
|---|---|
| Walrus/Tatum 集成 | Tatum事实是输入；Walrus规则决定是否追问与预算归类；真实读写回执和空状态恢复 |
| 技术质量 | 明确数据/用途边界、整数金额、幂等outbox、完整性校验、失败态、可执行用例 |
| 创意 | 以反例和规则作用范围为产品中心；让用户控制“记住以后怎么用” |
| 展示 | 三个页面、一项清楚任务、真实错误与修正、2–3分钟可复核的闭环 |
| Best Walrus Memory | 同输入历史对照、纠正影响下一次、跨表面恢复，而非仅展示12张记忆卡 |

主办方的计分维度与 memory 专项说明见[官方规则](https://thewalrussessions.wal.app/tatum-total-recall/)。本表是针对这些要求的工程映射，并不意味着评委会给满分。
